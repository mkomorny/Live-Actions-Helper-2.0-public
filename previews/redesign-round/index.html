1 · Four interface structures × eleven kits

Data is real: all 14 tools come from the actual tool.json manifests. The Live Set and tracks are a mock. Each kit's own tokens.css is included verbatim in themes/; a shared contract.css maps any kit's tokens onto the app's components.

A · Workbench

Tracks | catalog | inspector on the Actions page; Genius is full width with no track panel. CHOSEN.

Tool detail opens in the right pane and the catalog never leaves. The track list belongs to the Actions page only (Genius resolves tracks itself, so the Genius page has no track panel). Diagnostics live in a popover off the status pip; Preferences is a modal.

Trade-off: Best when you run many actions in a row against the same tracks; costs the most horizontal space.

B · Rail + slide-over

Icon rail, full-width card grid, slide-over detail.

No permanent sidebar. Targets is one header button that opens a picker with device lists. A tool slides over the catalog. Preferences is the last rail item; the bridge pip opens diagnostics.

Trade-off: Most room for the catalog and the calmest screen; track picking is one click deeper.

C · Command list

One column, search-first, grouped by what an action touches.

Actions are grouped into Selected tracks / Whole Set / Own dialog. A row expands in place (accordion). Targets is a chip strip pinned to the bottom. Search is the top bar. Preferences is a modal.

Trade-off: Fastest to scan and the most honest about scope; dense rows lose the card personality.

D · Session deck

Modelled on Live's Session View: track columns on top, master-detail below, Genius docked.

Tracks run across the top as columns you target. Tool list and the selected tool's detail sit side by side (never empty). Genius and the Console are tabs of a bottom dock, so Genius stops being a page.

Trade-off: Most Ableton-native and the biggest structural change; the least vertical room, and Genius becomes secondary.

3 · Platform ceiling: can Tkinter get there?

Same Actions screen, three runnable windows (source in tk/) plus the HTML version. Screenshots are real window captures.

Build 1 — Tk today. The app's own tokens and widget code, real manifests.

Build 2 — Tk pushed hard (Canvas + Pillow), palette read from the Cyber Neon Pink tokens.css.

Build 2 with the Riso kit. Colours follow; Riso's offset shadows don't, and the selected-row tint and scope pills stayed hard-coded from the pink theme — the selected rows are unreadable. Leaks like this are the ongoing cost of theming by hand.

Build 3 — HTML. Same theme, same screen, kit applied through the contract.

What the pushed Tk build cost (measured)

ApproachComponent code lines
Tk build 1 (today's style)61
Tk build 2 (pushed)196  — 3.2× build 1, for 6 components
HTML/CSS (same components)50 rule-lines (dense one-liners, so lines are not like-for-like) + a one-time 41-line theme contract

Per-component table and the list of what was not attempted (inputs, selects, chat, console, forms, modals, themed scrollbar): LOC-REPORT.md.

  • Looks: Tk build 2 gets convincingly close to a rounded, glowing kit — better than I expected. It does it with pictures: every button is a bitmap plus hand-written hover, press, focus, disabled, keyboard and resize code.
  • Theming: a kit file can drive only colours, radii and a font name in Tk. Shadows, motion, color-mix(), web fonts and every kit's layout.md stay inert. Themes are Python constants, not files someone can drop in.
  • Memory (private bytes, static page, whole process tree): Tk build 1 ≈ 26 MB (1 process); Tk build 2 ≈ 24 MB; a pywebview/WebView2 shell showing layout A ≈ 235 MB across 7 processes — about +209 MB. Startup time was not measured.
  • Already shipped dependency: webview_pane.py and three tools already use pywebview, and the module imports on this machine.

LIVE ACTIONS — APP DETAILS
==========================
Written from the code as of 17 August 2026.
Read this before you add a tool.

What this app is
----------------
Live Actions is a Windows desktop host for Ableton Live 12 Standard +
Max for Live. It is a homemade stand-in for Suite-only Ableton Extensions.

You pick tracks in the desktop window, open a tool, and that tool is
supposed to change only those tracks. Official Extensions use Live's
right-click menu. This app cannot add items to that menu. It talks to
the Set through a Max for Live audio effect on a track and the Live
Object Model (Live 12 manual chapter 31).

This is not official Ableton Extensions.
This is not official Producer Pal.
Do not patch or replace Producer_Pal.amxd from this project.

Repo: https://github.com/mkomorny/Live-Actions-Helper-2.0 (private; Live Actions Helper 2.0, all new work)
Original Tk app history: https://github.com/mkomorny/live-actions-helper


How the pieces fit
------------------
  Desktop window (Python / tkinter)
           |
           |  OSC on localhost only
           |  app -> bridge  UDP 11924
           |  bridge -> app  UDP 11925
           v
  Live Actions  (Max Audio Effect on a track)
           |
           |  Live Object Model  (live.path / LiveAPI)
           v
  The open Live Set

The window lists tools, remembers which tracks you ticked, and opens a
tool's own screen inside the same window. The bridge is what can read
and write Live. A tool that never talks to the bridge cannot change
the Set.

The device face has an **Open desktop host** button. Max for Live
blocks [system]/[shell], so the button opens liveactions://open
(registered by install.ps1) via max.launchbrowser() -- the only
mechanism that works inside the M4L sandbox. A second click raises
the existing window.

What you see in the window
--------------------------
Three top buttons (not extra windows):

  Actions   main screen
  Genius    copied Genius chat + library index
  Settings  API key, folders, ports

On Actions:

  Live Set          connection line, ping / status / refresh / reset
  Apply tools to    tick tracks. All / None / Live's selection
  Tools             one card per tools\<id>\tool.json
  Log

Click Open on a card. That tool's screen replaces the Actions body
inside this app. It is not a new top-level tab.

On a tool screen:

  colored banner from tool.json "accent"
  Back to tools
  the same track picker (shared ticks)
  fields from tool.json
  Run on selected tracks

Track targeting
---------------
A tool must not assume the whole Set.

  key examples:  midi:0   audio:2   return:0   master:0

First time tracks load, the default is Live's currently selected
track, not every track. All / None / Live's selection change the ticks.
The same ticks are used on the main screen and on the tool screen.

If nothing is ticked, Run stops and tells you to tick a track.

How a tool is discovered
------------------------
helper.py load_tools() does this:

  1. Look in Settings -> tools_dir (default: this project's tools\).
  2. Find every immediate child folder that contains tool.json.
  3. Parse JSON. Skip the file if it is invalid or has no "id".
  4. Sort by path. Each valid file becomes a card.

Refresh tools after you add or edit a manifest. You do not restart
Live for a JSON-only change. You do restart / re-drop the bridge if
you change live-actions-bridge.js -- copying the file to the User
Library is not enough by itself: Max only reloads it when the device
is removed and re-added to a track, so a device that was already
sitting on a track keeps running its old, in-memory copy of the
script otherwise. install.ps1 stamps a build id into every deploy
and pings the running device afterward to tell you which case you're
in -- "Confirmed" (the running device matches) or "STALE" (re-drop
it) -- instead of leaving that as a silent trap.


How to add a tool (UI first)
----------------------------
1. Create a folder:

     tools\my-tool\

2. Create tools\my-tool\tool.json. Required key: id.

     {
       "id": "my-tool",
       "name": "My Tool",
       "description": "One line. Shown on the card and on the tool screen.",
       "accent": "#34d399",
       "version": "0.1",
       "enabled": true,
       "fields": [
         {
           "id": "amount",
           "label": "Amount",
           "type": "text",
           "default": "50"
         }
       ]
     }

3. Click Refresh tools. Open the card. Confirm the screen and the
   track list.

4. That is only the screen unless the bridge knows that id.
   Breakdowns is implemented. Other ids still need a job in
   live-actions-bridge.js. See "How to make Run actually change Live".

A tool can also set "ui": "webview" and "dialog": "ui/dialog.html"
to embed an HTML dialog instead of text fields.

tool.json keys
--------------
  id            required. Sent as the first OSC argument to /live-actions/run
  name          card title and banner
  description   card subtitle and banner
  accent        hex color for the card border, Open button, and banner
  version       string, for you
  enabled       reserved; the host currently lists any file with an id
  fields        array of controls on the tool screen

Each field (the host only draws text boxes today):

  id            required. Becomes a key in the Run payload "fields"
  label         shown above the box
  type          reserved; treated as text
  default       starting value

Copy clip-namer or arrangement-skeleton and change the id.


What Run sends
--------------
If at least one track is ticked, the window sends:

  address   /live-actions/run
  arg 0     tool id string          e.g. clip-namer
  arg 1     JSON string:

    {
      "tracks": [
        {
          "key": "midi:0",
          "index": 0,
          "kind": "midi",
          "path": "live_set tracks 0"
        }
      ],
      "fields": {
        "pattern": "{track} {bar} take"
      }
    }

kind is midi, audio, return, or master.
path is the Live Object Model path the bridge can pass to LiveAPI.
index is 0-based inside that kind.

Use only payload.tracks. Do not walk the whole Set unless the user
clicked All.


OSC protocol
------------
App -> bridge  (UDP 127.0.0.1:11924)

  /live-actions/ping
  /live-actions/status
  /live-actions/tracks
  /live-actions/run          <id> <json>
  /live-actions/api/get      <lom-path> <property>
  /live-actions/api/set      <lom-path> <property> <value>
  /live-actions/api/call     <lom-path> <method> [args...]
  /live-actions/reset        clears a stranded bridge-side job and re-arms
                              ready; sent by the app's Reset button

Bridge -> app  (UDP 127.0.0.1:11925)

  /live-actions/hello        ready
  /live-actions/pong         timestamp
  /live-actions/status       JSON  {ok, name, tempo, tracks, time_signature}
  /live-actions/tracks       JSON  {ok, selected_id, tracks:[...]}
  /live-actions/result       ok|error  message
  /live-actions/api/reply    JSON  {ok, value?} or {ok:false, error}

/live-actions/reply and /live-actions/result are sent through the bridge's
sendChunked() (live-actions-bridge.js), not raw sendOsc: a payload over
4000 chars (REPLY_CHUNK_LIMIT; lowered from ~48KB in v1.0.32 -- that limit
still sat close enough to Max's own per-atom text ceiling that a large
Genius/Pal reply occasionally arrived at the app as a fully-reassembled but
EMPTY string, P4 A2) -- a Genius/Pal read against a large Set is the
realistic case -- goes out as several <key> <seq> <total> <chunk> messages
instead of one oversized datagram, since a single legally-sized-but-large
reply is still worth avoiding even though it fits under UDP's real ceiling.
Under that size the wire shape is unchanged: <key> <payload>, same as
before v1.0.12. BridgeClient._reassemble (app/bridge_client.py, moved out of
helper.py in v1.0.54) does the joining on
the app side. stringify() (bridge.js) escapes every non-ASCII character to
\uXXXX before chunking -- a JS string's .length is UTF-16 code units, not
bytes, so a track/clip name with real unicode could otherwise undercount
the actual atom size this limit is trying to stay under.

Do not construct LiveAPI in loadbang. The patch uses live.thisdevice
to bang init. Audio passes plugin~ -> plugout~. Put the device on an
audio track (or a MIDI track that already has an instrument).

BridgeClient's listener never dies on a bad or oversized packet (v1.0.12) --
on Windows, a UDP send into a port nothing is bound to yet queues an ICMP
error against the sending socket, and the next unrelated recvfrom() on that
same socket raises WSAECONNRESET; this used to kill the app's listener
thread permanently on the very first missed ping (e.g. before the device is
dropped, or mid re-drop). It now logs and keeps going. If the bridge still
looks dead, the sidebar's Reset button (next to Ping/Status/Sync) rebuilds
the app's socket and sends /live-actions/reset -- re-adding the device is
no longer the only way back.

udpreceive 11924 takes no arguments -- do not add @fullpacket or a bare
fullpacket argument. That switches udpreceive into raw OSC FullPacket mode
(one buffer object per packet), which dispatch() cannot read; it expects
decoded anything()/list() messages, the default. setStatus() (device face
text) sends outlet(1, ["set"].concat(words)) -- a "set" message with the
status text split into individual word atoms, not one atom. textedit does
not accept a bare string, and a single atom containing spaces round-trips
through Max's atom-to-text conversion wrapped in quotes.

If the bridge never reaches Connected at all -- Ping/Status time out on
every attempt, even right after a clean re-drop -- suspect a security
suite's own firewall (not Windows Firewall; confirmed clean on this dev
machine) silently dropping inbound UDP to Max.exe. See DEBUGGING TO DO
LIST.md #9 for the live diagnostic that isolates this to the network layer,
not the app.


How to make Run actually change Live
------------------------------------
live-actions-bridge.js handles the shipped ids (tool jobs live directly
in this file). live-actions-pal.js is pulled in via include() at the
bottom of it and adds the Pal-parity live_* jobs. Other ids still
reply with an error until you add a job.

To implement a job:

1. Keep the UI contract above (id + JSON payload).
2. Edit bridge/live-actions-bridge.js.
3. In dispatch(), when name === "live-actions/run", parse args[1]
   as JSON, read payload.tracks, and only touch those paths.
4. Use LiveAPI the same way statusJson / tracksJson already do.
   Example: new LiveAPI("live_set tracks 0") then get / set / call.
5. Copy the js next to the .amxd in the User Library. Remove the
   device from the track and drop it on again (or Edit in Max and
   save) so Live loads the new script.
6. Reply with /live-actions/result  ok  <short message>
   or /live-actions/result  error  <why>.

Generic Live API from the desktop (no new js job) is already there:

  /live-actions/api/get   live_set tracks 0   name
  /live-actions/api/set   live_set tracks 0   name   Kick
  /live-actions/api/call  live_set            create_midi_track  -1

A finished tool can use those from Python later, or stay entirely
in the Max js. Either way, honor the ticked tracks.


Current shipped tools
---------------------
  clip-namer
    Renames session clips on ticked tracks.
    Tokens: {track} {bar} {take} {index}

  arrangement-skeleton
    Drops Arrangement locators. Field: Intro 8, Verse 16, Chorus 16, Outro 8.
    Locators are Set-wide. No track tick required. Switch to Arrangement to see them.

  mutate
    Writes variation clips from the selected MIDI clip on a ticked track.
    Same drop / swap / velocity math as the Mutate MIDI Tool.

  empty-clips
    Creates an empty MIDI clip in the first empty slot on each ticked MIDI track.

  color-clips
    Sets clip color (#RRGGBB). also_scenes=yes colors those scenes too.

  duplicate-clips
    Copies every session clip on ticked tracks into empty slots.

  track-batch
    action: rename, arm, unarm, mute, unmute, send.
    rename uses {name} {kind} {index}. send uses letter A/B/C and 0-1.

  reveal-device
    Selects a device whose name contains the field (Chord Explorer, Dub Assistant…).
    The device must already be on a ticked track.

  breakdowns
    Full dialog (the Breakdowns engine + UI, MIT, from
    github.com/dnvsfn/ableton-breakdowns). Opens as its own window
    (pywebview / Edge). Audition is local Web Audio and writes
    nothing. Insert fill sends /live-actions/run breakdowns with
    pitched MIDI notes.

    Insert as (user picks each time):
      newClip     first empty session slot on each ticked MIDI track
      replace     overwrite the MIDI clip selected in Live
      append      add the fill at the end of that selected clip
      newTrack    create one MIDI track + clip
      playhead    Arrangement clip at the song playhead

    tool.json uses "ui": "webview" and "dialog": "ui/dialog.html".
    Rebuild the dialog with:  npm install && npm run build
    inside tools\breakdowns. After changing the bridge js, copy it
    next to the User Library .amxd and re-drop the device.

    The webview host (app/webview_pane.py, app/breakdowns_window.py) is
    shared by every "ui": "webview" tool, not specific to Breakdowns --
    helper.py's _webview_context()/_on_webview_message() dispatch by
    tool.json's "id" to add a new one. A per-monitor-DPI-unaware
    pywebview window opened from a background process on a scaled
    display does not become visible or focusable on its own (Windows'
    foreground-lock policy blocks it, and the WS_VISIBLE style bit was
    observed never getting set): webview_pane.py grants the spawned
    dialog foreground rights via AllowSetForegroundWindow right after
    Popen (this process just handled a real click, so it has standing
    to grant that), and breakdowns_window.py claims them with
    ShowWindow(SW_SHOW) + SetForegroundWindow once its "shown" event
    fires. Found and fixed 2026-08-19 -- previously the dialog opened
    correctly-positioned but invisible until manually alt-tabbed to.

    The redesign's WebView2 shell (a MAIN window, not a child dialog
    spawned right after a click -- so it has no parent to grant it
    AllowSetForegroundWindow) was separately spike-tested 2026-09-20 and
    does NOT reproduce this quirk: SetProcessDpiAwareness(2) +
    ShowWindow/SetForegroundWindow/BringWindowToTop on the "shown" event
    is enough on its own. See docs/plans/v1.0.56-slice1-spike-a-and-b.md
    (the throwaway spike harness was deleted in v1.0.57; the real shell,
    app/shell.py, uses the same logic via app/single_instance.py).

  detect-key
    Finds the key (and mode) of a MIDI clip, ticked track(s), or the
    whole Set. Krumhansl-Schmuckler-style: literature pitch-class weight
    tables (krumhansl-kessler or temperley) correlated against clip
    content, combined with structural evidence -- bass, downbeats, and
    cadence position -- to name both the diatonic collection and which
    of its 7 degrees is the tonic, across 7 scale families (Major,
    Minor, Dorian, Phrygian, Lydian, Mixolydian, Locrian) x 12 roots.
    Top N results (field: results, default 3), best match first, close
    call flagged right after the top pick so it isn't cut off by the
    result string's length limits, e.g.
    "D Dorian 100% (close: C Major) · A Minor 91% -- 412 notes, 6 clips".

    Fields: scope (clip/track/set, default clip), profile
    (krumhansl-kessler/temperley), results (1-12, default 3).
    No track tick required for scope clip or set (tool.json sets
    top-level "scope":"set" so the host doesn't block Run); tick
    MIDI track(s) first for scope track.

    Same 7 notes can be 7 different modes -- C D E F G A B is C Major,
    D Dorian, A Minor, and more, and the note *set* alone can't say
    which. Home is picked from three signals outside the pitch-class
    set: which pitch anchors the bass, which pitches land on downbeats,
    and which pitches the phrase resolves to at the end (cadences weigh
    more than pickups). This is statistical scoring, not a guarantee --
    sparse, rootless, or non-cadential material (a static pad with no
    clear bass or ending) can still tie, and the tool reports that
    honestly ("close call") instead of asserting a false-confident
    winner. See the comment above detectKeys() in live-actions-bridge.js
    and docs/plans/v1.0.4-key-detection-two-pass.md for the full design
    and reasoning, including why an earlier same-version attempt at this
    (reweighting one shared histogram) could not work.

    Track/set scope pools every clip's evidence into one combined
    picture -- that answers "what does this track/Set lean toward,"
    not "this has one single tonic." The result message says so when
    more than one clip contributed.

    Reachable from the Tools tab and from Genius (live_detect_key --
    Genius must call the tool, never guess a key from raw note data).

  bbencut (shipped v1.0.10)
    Algorithmic breakbeat cutting (BBCut2/BBenCut, MIT, ported from
    github.com/bencodec/BBenCut, a Suite-only Extension this app
    substitutes for). Opens as its own dialog window (pywebview /
    Edge), same shared webview host as Breakdowns. Pick one of 10 cut
    procedures, set its README-documented parameters plus Total/Loop
    length in beats, Apply computes the cut sequence client-side.

    Tick exactly one audio track, then double-click the source
    Arrangement audio clip on that track to load it into Detail View
    -- that is BBenCut's source-clip anchor (there is no Arrangement
    time-selection exposed to Max for Live's LiveAPI, so this app
    can't read "the selected range" the way the original Extension
    did; Total/Loop length are honest, freely-editable fields instead,
    not derived from a real selection).

    Apply sends the computed slices to the bridge's runBbencut job,
    which resolves the real sample file + Arrangement position from
    the Detail clip (Live 12 Beta: file_path is on the Clip object,
    not a Sample child), clears that range, and places each slice
    as a real Arrangement clip. Regular slices are created from the
    Detail clip's sample. Rendered roll groups are created from the
    ffmpeg WAV Python substituted into that slice's filePath -- the
    placement loop must not ignore that path (live-caught: using the
    source sample for every create_audio_clip filled roll slots with
    the start of the original break). Every placed clip is forced unlooped
    and cropped via loop_end/end_marker (the same mechanism
    setClipLength() uses) -- live-probed against Live 12 Beta:
    looping=1 does not let the LiveAPI control a clip's Arrangement
    span (end_time stays full-sample), and clip.set("length"/
    "end_time") silently no-op, so those are not used. BBenCut's own
    ported algorithm marks every real slice as "looping" internally
    (a repeat-to-fill-the-slot request); since that can't be honored
    here, a slice whose intended loop window is narrower than its
    Arrangement slot plays extra real source material instead of
    repeating -- runBbencut counts this and reports it in the result
    message rather than leaving a gap or faking a loop. Placed clips
    are fresh copies of the source file, not the source clip object --
    warp markers, warp mode, gain, and pitch are not carried over yet;
    test on an unwarped or simply-warped-at-song-tempo break.

    Roll-group slices (very short cuts BBenCut normally pre-renders to
    a WAV) are pre-rendered via ffmpeg (app\bbencut\roll_render.py) on
    a worker thread before the run is sent to the bridge -- but ONLY
    when the source clip is unwarped. That's a deliberate Pass-1 gate,
    not a missing feature: ffmpeg needs real seconds, and this tool has
    no way to read Ableton's warp-marker geometry, so it does not
    guess a beats-to-seconds mapping for a warped source. A warped
    source clip still places every non-roll slice correctly; only its
    roll groups keep being skipped and reported, with a clear per-
    group reason (warped source, tempo unavailable, missing file, or a
    cut past the end of the source file -- rejected, never silently
    clamped). Rendered WAVs land under <Ableton Samples folder>\BBenCut
    Rolls\, not a temp folder, so Collect All & Save keeps finding them.
    Rendered roll clips are still forced warping=1 like every other
    placed clip (see above) -- Live's own warp engine re-normalizes
    the clip's Arrangement span regardless of the extracted WAV's real
    length, so a wrong beats-to-seconds guess would grab the wrong
    grain of audio, not misplace the clip.

    Before any of the above happens, Apply now shows a blocking "Confirm
    Placement" dialog (Tk messagebox.askyesno) stating the exact clip
    count and that this is that many individual undo steps, not one
    atomic action -- this app has no transaction wrap anywhere. Decline
    and nothing is sent. Above a hard BAKE_THRESHOLD (80 clips,
    app\bbencut\bake_render.py -- inherited from the master plan's own
    suggestion, not yet live-timed against this machine; see the
    elapsed-ms figure runBbencut now logs on every run for that
    measurement) the run is never placed as individual clips at all:
    on an unwarped source it's baked into one WAV (ffmpeg atrim+concat
    across every slice, same mechanism as roll rendering, just the
    whole run instead of one small group) and placed as a single
    Arrangement clip -- one undo step, not eighty-plus -- after a
    separate "Confirm Bake" dialog. On a warped source over the
    threshold, the run is refused outright with a clear reason; there
    is no unsafe fallback that just floods the placement loop anyway.
    Rendered bakes land under <Ableton Samples folder>\BBenCut Bakes\,
    same reasoning as the Rolls folder. A failed source-clip read now
    blocks the whole run rather than degrading gracefully -- Step 5
    would still send with roll slices left unrendered; Step 6 treats
    "can't confirm what's about to happen" as a hard stop everywhere
    a confirmation dialog exists.

    The master plan's "OSC flooding" concern for large runs turned out
    not to match the real architecture: runBbencut is one synchronous
    loop inside a single Max js-engine call, not a series of per-clip
    OSC round-trips. The actual risk is Live's UI blocking for however
    long that loop takes with no progress shown -- Task-based chunking
    (the same pattern runSkeleton already uses) is deliberately NOT
    built this pass; the bake threshold already bounds the worst case,
    and building a tick-based state machine against an unmeasured
    number would be solving a problem nobody has confirmed exists yet.
    The new elapsed-ms logging is how that gets a real number before
    anyone decides to build it.

    tool.json uses "ui": "webview" and "dialog": "ui/dialog.html".
    Rebuild the dialog with: npm install && npm run build inside
    tools\bbencut. After changing the bridge js, copy it next to the
    User Library .amxd and re-drop the device.

There is still no Browser / BrowserItem class in the Live Object Model
exposed to Max for Live, so nothing here can walk Live's browser for
packs/presets/plug-ins -- those stay drag-and-drop only (unless engine
E2 is online -- see "Live browser access" in README.md -- in which case
live_load_browser_item can add them). Loading a sample onto a Drum Rack
pad doesn't need the browser, though: Genius can search samples_dir
(live_find_samples / live_library), then set a device param named
p<note>/sample (e.g. pC1/sample) to the found absolute path.
live_update_device creates the pad's chain (RackDevice.insert_chain,
Live 12.3+), puts a Simpler on it (Chain.insert_device, Live 12.3+,
native only), and loads the file (SimplerDevice.replace_sample). The
same path (palAssignDeviceSample) also loads a sample directly into a
Simpler already on a track, not just a Drum Rack pad.

Genius knows the actual running Live version (v1.3.0, app/live_version.py,
recorded from live_connect and the Remote Script ping) and states whether
replace_sample exists in that build as a resolved fact rather than a fixed
"needs 12.4+" claim. Whether or not the version check passes, the bridge
verifies the load by reading the device's own sample.file_path back after
calling replace_sample -- Max's LiveAPI.call on a rejected method can post
to the Max Console instead of throwing, so a clean call is not proof the
file loaded. On a mismatch, params_skipped/error names the real reason
(the actual exception, or what the device's sample actually holds) and
points at live_create_clip sample_file / live_load_browser_item as the
next tool call -- there is no "tell the user to drag it in by hand" path
left in the prompt; a genuinely older build gets an honest, specific
explanation from the read-back instead.

Open Producer Pal Local from the Genius menu only if you want the

What you must not do
--------------------
  Do not add items to Live's native right-click menu. Standard cannot.
  Do not put Settings -> Extensions packages here. That host is Suite.
  Do not edit C:\Users\<you>\My Apps\producer-pal-genius
  Do not edit C:\Users\<you>\My Apps\producer-pal-local
  Do not edit any Producer_Pal.amxd
  Do not put API keys in this folder. They belong in AppData.
  Do not run tools against every track unless the user clicked All.


Quick checklist for a new tool
------------------------------
  [ ] tools\<id>\tool.json with a unique id, name, description, accent
  [ ] Refresh tools, open the card, confirm the screen
  [ ] Track picker shows, ticks persist, Run refuses zero tracks
  [ ] live-actions-bridge.js handles that id and only payload.tracks
  [ ] js copied next to the User Library .amxd and the device reloaded
  [ ] /live-actions/result reports ok or error
  [ ] Nothing official Pal / Suite Extensions was touched


Versions and restore
---------------------
Repo: https://github.com/mkomorny/Live-Actions-Helper-2.0 (private)
Remote name in the working folder: helper2. Since v1.0.67 the working folder
"Live Actions Helper" is on main, and main pushes to helper2's main.
The old repo (remote origin, https://github.com/mkomorny/live-actions-helper) keeps the
original Tk app (its main = v1.0.53); its old redesign branch was deleted in v1.0.68
(the v1.0.46-v1.0.64 tags keep those commits reachable there, and the 2.0 repo has them all).
The way back to the Tk app: git checkout v1.0.53, or the classic-Tk launcher.

Every shipped update gets an annotated git tag (vX.Y.Z) pushed to
helper2 right after the commit, so each version is independently
restorable straight from GitHub -- not just the latest main. GitHub
serves an auto-generated zip/tarball for any tag with no extra setup:

  https://github.com/mkomorny/Live-Actions-Helper-2.0/archive/refs/tags/v1.0.3.zip

Restore a specific version:

  git clone https://github.com/mkomorny/Live-Actions-Helper-2.0.git
  cd Live-Actions-Helper-2.0
  git checkout v1.0.3

Then, same as a fresh clone:
  1. cd tools\breakdowns && npm ci        (rebuilds the Breakdowns dialog;
     deterministic from the committed package-lock.json)
  2. Run install.ps1 from the repo root.
  3. Re-enter Settings-tab values (API key, folders) -- these live in
     %APPDATA%\Live Actions\settings.json, which is intentionally not
     in the repo.

What a tag does NOT carry, by design (see .gitignore):
  %APPDATA%\Live Actions\settings.json   (API key, folder paths)
  tools\breakdowns\node_modules\         (rebuild with npm ci)
  app\__pycache__\, .remember\           (not app state)

Tags start at v1.0.1 (backfilled onto the commit that shipped it;
v0.1.0-v1.0.0 predate a reliable commit mapping and were not tagged).
